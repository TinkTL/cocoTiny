# 支付接口 Vercel WAF 限流设计

日期：2026-07-23

## 目标

在请求到达 Next.js Function 和支付宝 SDK 前，限制匿名来源对支付创建与主动查单接口的调用频率，降低恶意刷量、支付宝接口频控和 Vercel 资源耗尽风险。

## 实现方案

使用 Vercel WAF 的单条 Rate Limit 规则，不增加应用依赖或外部限流存储。

规则匹配以下两类请求：

- `POST /api/payments/alipay/create`
- `GET /api/payments/alipay/query`

限流维度为客户端来源 IP，固定窗口内每分钟最多允许 10 次匹配请求。超过阈值的请求由 Vercel WAF 返回 HTTP 429，不再进入应用 Function。

## 明确排除

以下端点不纳入该规则：

- `POST /api/payments/alipay/notify`

支付宝异步通知必须保持可达，且可能因网络或业务状态发生合法重试。通知安全继续依赖 RSA2 验签、应用身份、商户身份、订单号、金额及交易状态校验。

普通页面、静态资产、支付结果页和其他 API 不受本规则影响。

## 选择理由

- WAF 在应用代码执行前拦截，能够直接减少 Function 调用。
- Vercel 多实例之间共享规则状态，避免进程内限流失效。
- 当前 Hobby 项目包含一条限流规则，单条规则可以覆盖两个支付端点。
- 每分钟 10 次足以覆盖正常用户创建支付、返回结果页及少量手动重查。

## 预期行为

- 同一来源 IP 在一分钟内前 10 次匹配请求正常进入应用。
- 同一分钟内后续匹配请求返回 429。
- 窗口重置后恢复访问。
- 不匹配的站点请求不计入此限额。
- 支付宝异步通知不计入此限额。

共享公网出口下的多名用户会共用同一 IP 限额。当前站点流量较低，可以接受这一取舍；流量增长后应改为更精细的令牌或会话维度限流。

## 配置安全

- 规则必须同时约束请求路径和 HTTP 方法，避免误伤同名路径的其他行为。
- 应用规则前确认预览中的匹配条件和处置为 Rate Limit/429。
- 不配置基于请求头中可伪造 IP 的自定义键，使用 Vercel 识别的来源 IP。
- 保留 Vercel Firewall 审计记录，出现误拦时可立即回滚。

## 验收

1. 正常访问站点页面仍返回 200。
2. 单次支付创建请求正常返回支付链接。
3. 单次合法订单查询正常返回订单状态。
4. 对受保护接口连续请求超过阈值后出现 429。
5. 检查 Vercel Runtime Logs，确认被 WAF 拦截的请求没有进入 Function。
6. 确认异步通知路径没有被规则匹配。

验证时不创建新的真实付款，不重复扣款，并优先使用无效订单号测试查询接口限流。

## 后续工作

限流完成后，单独设计无登录购买模型：

- Neon Postgres 持久化订单。
- 随机高熵购买凭证，仅保存哈希。
- 购买凭证与订单、资产包和支付状态绑定。
- 下载接口校验已支付订单和有效凭证。
- 支付宝异步通知使用数据库事务和唯一约束实现幂等。
